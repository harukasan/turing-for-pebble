# Web and watchface behavior

## Web controls

The default implementation is the watch build, Q15 16-bit storage at 120 × 136, shown with interpolation. The implementation selector also offers Float32 at 120 × 136, Q15 at 100 × 114, 200 × 228 with one packed 16-bit word per cell (A as a 7-bit linear code and B as a 9-bit square-root companded code, written with dithered error diffusion), Float32 at 200 × 228, and Float32 at 100 × 114. The same-resolution pairs isolate numerical and storage differences from grid resolution. Switching implementations frees the old Wasm allocation when applicable and initializes the selected mode with the same seed. Changing the seed or preset also resets the field. Switching does not retain or synchronize elapsed steps, so compare the same seed, parameters, and displayed step count. Feed, Kill, diffusion, and timestep controls apply to the current field on the next step.

The Float32 options run the original `Simulation.step` implementation. Their initial 24 disks are placed using the C core's display-coordinate LCG, periodic distance, and radius range. The Q15 mode has exactly the same initial concentrations. The packed mode starts from A = 64/127 instead of 0.5, while its B = 0.25 is exact. Interactive seeds also use display coordinates. Float32 computes with JavaScript number intermediates and stores each field in `Float32Array`. Its result is a reference for visual comparison, not a numerically identical Pebble build.

計算セルの間を補間 switches between interpolated rendering (`RD_ROW_BILINEAR`) and showing the cell under each pixel. The Float32 engines interpolate their float B at the same positions.

文字盤 selects the digital or the analog clock face (`RD_FACE` on the watch, below). 現在時刻 shows the current time. Turning it off starts from the current minute and shows a slider over the minutes of the day (0 to 1439, labeled HH:MM) that sets the time drawn and masked by either face on today's date, so the analog hands can be scrubbed to any position. The slider is a preview control and is not recorded in the settings JSON or `config.h`, while the face is.

Pause, speed, 100-step advance, pointer seeding, palettes, display scaling, PNG, and JSON controls remain. Wasm and clock-font loading failures produce a visible error and stop simulation. Selecting Float32 is explicit, never a silent fallback. Wasm linear memory is fixed and the rendering arrays are reused. The Float32 renderer writes into the same reusable `ImageData`.

The JSON output records requested and effective parameters, implementation, storage, rounding, seed, version, dimensions, palette, and step count. In the Q15 modes the effective diffusion coefficients are the folded values the core computes with, `round(D × 32768 / 20) × 20 / 32768`. Float32 records its requested parameters as effective because Q15 conversion is not applied. It is a settings record, not a state snapshot. Parameter history and hand-painted seeds are not serialized. `config.h` output is enabled for Wasm modes and supplies the same effective parameters and seed for a Pebble build. On-watch RGB2 output is always quantized, even if the Web's smooth-color preview option is enabled. Smartphone settings are out of scope.

The new **細線** preset uses Feed 0.023 and Kill 0.052. With seed 42 at 10,000 steps, the 200 × 228 packed mode develops narrow curved bands. The 100 × 114 Q15 mode retains the structure with visibly wider bands. [The comparison image](../public/reports/thin-lines.png) shows these two outputs side by side at native display size, high resolution on the left. This is a deliberately difficult case for a coarse grid, not a guarantee of the same geometry across implementations.

## Clock

Two font sets are available, selected by `RD_FONT` on the watch and the 時計フォント control on the Web:

| Set    | Time                    | Date                        |
| ------ | ----------------------- | --------------------------- |
| LECO   | LECO_42_NUMBERS at y=78 | LECO_20_BOLD_NUMBERS, y=128 |
| Bitham | BITHAM_42_BOLD at y=79  | BITHAM_30_BLACK at y=122    |

Bitham has no small font with digits, so its date uses BITHAM_30_BLACK. The Bitham tops center the digit 0 on the LECO digit centers. Lines are horizontally centered. The Web draws extracted 1-bit glyphs without antialiasing. The watch draws the glyphs itself into the framebuffer from the core's copy of the system font glyphs (`cm_draw`), which gives the same pixels as `graphics_draw_text` and is faster. It falls back to the system fonts only when the framebuffer cannot be captured, and the analog face then draws its hands as system lines of about the same width. White glyphs are drawn directly over the pattern without a background panel.

With digit avoidance (`RD_AVOID`, default on except in mode 0 on the watch, and 数字を避ける on the Web, on by default for every engine), B is held at 0 in the grid cells under the digits, widened by a 1-pixel halo (`RD_HALO`), and the kill rate rises to 0.075 over the 5 cells around them. The pattern fades out a few cells before the digits without a band along their outline, and the masked cells show the background color. The mask is rebuilt from the same time as the drawn text at startup and at every minute change. Each minute change then raises the pending steps to 300 (`RD_MINUTE_STEPS`) so the strokes freed by the previous digits refill. Mode 0 keeps 16 steps per minute and no mask, because a 300-step burst would take about 24 s there.

The analog face (`RD_FACE` 1 on the watch, built as `mode-3-analog`, and アナログ on the Web) draws an hour hand, a minute hand, a center disk, and the date line of the selected font set. Angles are in units of 1/1440 of a turn (0.25°) clockwise from 12 o'clock: the minute hand is at `minute × 24` and the hour hand at `(hour mod 12) × 120 + minute × 2`, so a minute moves them by 24 and 2 units. The dial center is display pixel (100, 104). The minute hand is 80 pixels long with a radius of 2, the hour hand 54 pixels with a radius of 3, both with round tips, and the center disk has a radius of 5. Together they stay within columns 18 to 182 and rows 22 to 186. The date line is centered as in the digital face, with its text box at y=204 for LECO (digit rows 210 to 223) and y=192 for Bitham (digit rows 201 to 221), below the reach of the hands. The pixels come from the core (`cm_build_analog`, [Shared C core](core.md)): the Web draws the 200 × 228 halo 0 bitmap, and the watch draws the same pixels into the framebuffer through `cm_draw_analog`. The hands and the date are white and drawn directly over the pattern like the digits. With avoidance (針と数字を避ける on the Web), the cells under the hands, the disk, and the date are masked with the same halo and kill ramp as the digits, so the pattern fades out around the hands. The masked rows then span the dial: in mode 3 the rows that read the mask levels average about 102 of 136 over the 720 times of a half day, against about 44 for the digits.

## Scheduling

Interactive Web mode renders up to 30 times per second. It checks elapsed compute time after each complete step and yields after approximately 8 ms. One complete step can exceed the budget. The Speed slider sets the steps attempted per frame within that budget, and the 100-step advance runs up to 8 steps per frame within it.

The Web no longer simulates the watch's startup, minute-work queue, or backlight scheduling. It remains an interactive comparison view. It does sweep the analog hands as the watch does: when the shown minute changes, by the clock or the time slider, the hands ease from their shown angles to the new ones over 1 s (`SWEEP_MS`) through the core's `cm_sweep_angle`, and the mask of either engine is rebuilt only in frames where an integer angle changed. The exported `config.h` retains the watch's scheduling constants, and settings JSON records the minute-step count.

The watch uses SDK BacklightService and AppFocusService. It does not subscribe to accelerometer data. Startup runs in timer slices for `RD_STARTUP_MS` (30 s) after launch, or until `RD_STARTUP_STEPS_MAX` (2,500) steps, about 45 s at the measured rate, whichever comes first, which is about 1,650 steps in mode 3 on the physical Pebble Time 2. A minute change during the startup is covered by the startup steps, and only the steps it is still owed at the deadline run after it. The deadline is wall time since launch, so time spent unfocused during the startup counts against it. Minute updates rebuild the digit mask and raise the pending steps to 300 (16 more without avoidance). With the analog face a minute update that arrives while focused instead starts a sweep: over `RD_SWEEP_MS` (1 s) each slice first moves the hands to their eased angles (`cm_sweep_angle`, a quadratic ease-out along the shorter way round, so 11:59 to 12:00 passes through 1439 to 0), rebuilds the mask within the 30 ms slice budget whenever an integer angle changed, and then runs steps as usual. A minute moves the minute hand 24 units and the hour hand 2, so a sweep rebuilds the mask at most 26 times, and fewer in practice, because slices come about every 40 ms and the ease-out slows the last units. The count is logged per sweep ([Validation](validation.md)). The slices continue while the sweep runs even when no steps are pending, and a slice that moved the hands redraws under the same 50 ms throttle. The final slice snaps to the target angles. A focus loss snaps a running sweep to its target, and a minute update while unfocused sets the new angles at once, so the drawn hands always equal the masked ones. While work is pending, each callback runs steps until a 30 ms budget is used, checked after every complete step (three steps of about 14 ms in mode 3), then reschedules itself 1 ms later. The layer is marked dirty once another slice would pass 50 ms since the last mark, which gives about 20 frames per second against the OS ceiling of about 27, and when the queue empties. Backlight animation runs the same 30 ms slices and 50 ms redraws for at most five seconds, and draws the last computed steps when the window ends. Focus loss cancels timers and ends a backlight window, and backlight-on is ignored while unfocused. Focus restoration resumes pending work. Backlight-off cancels animation while pending startup or minute work remains eligible for timer execution. A separate five-second timer bounds each backlight animation window. The field is blitted into the framebuffer as ARGB8 rows from `rd_row_rgb2` with `RD_RENDER_FLAGS` (interpolated in mode 3) within the unobstructed bounds, and the clock fonts are loaded once at startup.

Timing uses the public `time_ms` API. The emulator's wall-clock seconds and tick-derived millisecond component can be discontinuous. Negative or unexpectedly large deltas end the current slice and mark timing diagnostics invalid. Such values must not be interpreted as a valid benchmark or used to select a production mode. The watch measured the 30 ms slices and 50 ms frames of this pacing directly ([Validation](validation.md)). Production builds have no logs. A build with `RD_BUILD_LOG=1` (or `RD_BUILD_PROFILE=1`, `RD_BENCH`, or `RD_FRAME_BENCH`) logs `RD init` at launch, four `RD startup` lines when the startup and any refill it still owes have finished (validated wall time, steps per second times 10, the average step, field, and text times, the minimum free heap, and whether a focus loss or a gap of 5 s or more between slices interrupted the run or the clock invalidated it), an `RD mode` progress line every 256 steps (`RD prof` lines with `RD_BUILD_PROFILE=1`, which also runs a clock calibration loop), `RD light` with the steps and frames of each backlight window, and, with the analog face, `RD sweep` at the end of each sweep with its mask rebuilds, their longest time, its duration, and the steps run during it.

## Memory reporting

The Web UI shows one memory figure for the selected implementation: the total core allocation reported by the C core for the Wasm modes (fields, scratch rows, control data, the rendering rows and tables, alignment, and the digit mask levels), or the four JavaScript concentration arrays for Float32. The watch's clock mask bitmap is a separate allocation outside the core. Build sizes, compiler stack reports, and the physical measurement of the watch (startup, steps per second, minimum free heap) are in [Validation](validation.md) and `public/reports/comparison.json`. Runtime minimum free heap already includes allocations and must not be added to an estimate of remaining heap.

The acceptance thresholds are a 128 KiB app region and at least 16 KiB minimum free heap during normal operation. Compiler stack reports describe application functions. OS and library stack contributions are additional. Mode 3 is the watch build.
