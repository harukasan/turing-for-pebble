# Web and watchface behavior

## Web controls

The default implementation is the watch build, Q15 16-bit storage at 120 × 136, shown with interpolation. The implementation selector also offers Float32 at 120 × 136, Q15 at 100 × 114, 200 × 228 with one packed 16-bit word per cell (A as a 7-bit linear code and B as a 9-bit square-root companded code, written with dithered error diffusion), Float32 at 200 × 228, and Float32 at 100 × 114. The same-resolution pairs isolate numerical and storage differences from grid resolution. Switching implementations frees the old Wasm allocation when applicable and initializes the selected mode with the same seed. Changing the seed or preset also resets the field. Switching does not retain or synchronize elapsed steps, so compare the same seed, parameters, and displayed step count. Feed, Kill, diffusion, and timestep controls apply to the current field on the next step.

The Float32 options run the original `Simulation.step` implementation. Their initial 24 disks are placed using the C core's display-coordinate LCG, periodic distance, and radius range. The Q15 mode has exactly the same initial concentrations. The packed mode starts from A = 64/127 instead of 0.5, while its B = 0.25 is exact. Interactive seeds also use display coordinates. Float32 computes with JavaScript number intermediates and stores each field in `Float32Array`. Its result is a reference for visual comparison, not a numerically identical Pebble build.

計算セルの間を補間 switches between interpolated rendering (`RD_ROW_BILINEAR`) and showing the cell under each pixel. The Float32 engines interpolate their float B at the same positions.

Pause, speed, 100-step advance, pointer seeding, palettes, display scaling, PNG, and JSON controls remain. Wasm and clock-font loading failures produce a visible error and stop simulation. Selecting Float32 is explicit, never a silent fallback. Wasm linear memory is fixed and the rendering arrays are reused. The Float32 renderer writes into the same reusable `ImageData`.

The JSON output records requested and effective parameters, implementation, storage, rounding, seed, version, dimensions, palette, and step count. In the Q15 modes the effective diffusion coefficients are the folded values the core computes with, `round(D × 32768 / 20) × 20 / 32768`. Float32 records its requested parameters as effective because Q15 conversion is not applied. It is a settings record, not a state snapshot. Parameter history and hand-painted seeds are not serialized. `config.h` output is enabled for Wasm modes. It writes the watch's build header with the mode, seed, and rendering, and the effective parameters, palette, clock font, avoidance, and clock as the `RD_DEFAULT_*` settings the face shows until the phone sends its own. On-watch RGB2 output is always quantized, even if the Web's smooth-color preview option is enabled. The watch's own settings page is described under [Watch settings](#watch-settings).

The new **細線** preset uses Feed 0.023 and Kill 0.052. With seed 42 at 10,000 steps, the 200 × 228 packed mode develops narrow curved bands. The 100 × 114 Q15 mode retains the structure with visibly wider bands. [The comparison image](../public/reports/thin-lines.png) shows these two outputs side by side at native display size, high resolution on the left. This is a deliberately difficult case for a coarse grid, not a guarantee of the same geometry across implementations.

## Clock

Two font sets are available, selected by the font setting on the watch, or fixed by `RD_BUILD_FONT`, and by the 時計フォント control on the Web:

| Set    | Time                    | Date                        |
| ------ | ----------------------- | --------------------------- |
| LECO   | LECO_42_NUMBERS at y=78 | LECO_20_BOLD_NUMBERS, y=128 |
| Bitham | BITHAM_42_BOLD at y=79  | BITHAM_30_BLACK at y=122    |

Bitham has no small font with digits, so its date uses BITHAM_30_BLACK. The Bitham tops center the digit 0 on the LECO digit centers. Lines are horizontally centered. The Web draws extracted 1-bit glyphs without antialiasing. The watch draws the glyphs itself into the framebuffer from the core's copy of the system font glyphs (`cm_draw`), which gives the same pixels as `graphics_draw_text` and is faster. It falls back to the system fonts only when the framebuffer cannot be captured. White glyphs are drawn directly over the pattern without a background panel.

With digit avoidance (the avoidance setting on the watch, on by default and unavailable in mode 0, which is built without the mask area, and 数字を避ける on the Web, on by default for every engine), B is held at 0 in the grid cells under the digits, widened by a 1-pixel halo (`RD_HALO`), and the kill rate rises to 0.075 over the 5 cells around them. The pattern fades out a few cells before the digits without a band along their outline, and the masked cells show the background color. The mask is rebuilt from the same time as the drawn text at startup and at every minute change. Each minute change then raises the pending steps to 300 (`RD_MINUTE_STEPS_AVOID`) so the strokes freed by the previous digits refill. Mode 0 keeps 16 steps per minute and no mask, because a 300-step burst would take about 24 s there.

## Watch settings

The Pebble app's settings button opens a settings page for the watchface. The page and the watch share eleven integer settings, sent under the message keys of `pebble/package.json`:

| Setting          | Values                                                  | Default                        |
| ---------------- | ------------------------------------------------------- | ------------------------------ |
| `FEED`, `KILL`   | Q15, 0 to 32768                                         | 950 and 1868, the 迷路 preset  |
| `DA`, `DB`, `DT` | Q15, 0 to 32768                                         | 32768, 16384, and 32768        |
| `PALETTE`        | 0 to 8 for the built-in palettes, 9 for the custom one  | 0, lime                        |
| `LOW`, `HIGH`    | Dark and light stops of the custom palette, 0xRRGGBB    | The lime stops                 |
| `FONT`           | 0 LECO, 1 Bitham                                        | 0                              |
| `AVOID`, `CLOCK` | 0 or 1                                                  | 1                              |

The defaults are the `RD_DEFAULT_*` values of `pebble/src/c/config.h`. Everything else, including the mode, the seed, the rendering, the startup length, the halo, and the minute steps, stays fixed at build time.

The page (`src/settings/`) offers the five presets by name and カスタム with Feed and Kill sliders, Da, Db, and Dt sliders within the Web demo's ranges, the nine built-in palettes with swatches of their quantized colors and a custom palette whose dark and light stops are picked from the watch's 64 colors, the clock font, 時刻・日付を表示, and 数字を避ける, which needs the clock. A preview above the controls runs the shared core as WebAssembly in mode 3 with seed 42, the watch's digit mask, and quantized interpolated rendering for 1,650 steps, about the steps of the watch's startup, at twice the watch's pace so that it grows in 15 s, and draws the clock with the phone's time. `PREVIEW_SPEED` in `src/settings/preview.ts` sets the pace. A change of coefficients, font, or clock runs the preview again after 300 ms, and a palette change only recolors it. The preview's field is the watch's field, which the tests check against the golden hashes. 保存 returns the settings as JSON through `pebblejs://close#`, or through the `return_to` address that `pebble emu-app-config` adds, and キャンセル closes the page without them.

The page is embedded in the phone script. The phone opens it as a `data:` URL of about 100 KB with the stored settings in it, so it needs no hosting and works offline. A build with `RD_BUILD_CONFIG_URL` opens that address instead, with the settings in the query string. The phone script stores the settings the page returns, sends them to the watch, and sends its stored copy again when the face starts, for example after a reinstall. It sends only settings whose every value is in range.

The watch applies a message only if every value it carries is in range. It stores the settings as one versioned persist blob and reads the blob back at launch with the same checks, falling back to the defaults. New coefficients restart the field from the seed and run the 30 s startup again. Removing the digit mask, by turning the clock or avoidance off, restarts the field the same way, because the empty area under the former digits would take hours to fill at the minute steps without avoidance. A new font or a new mask refills like a minute change with 300 pending steps, and a palette change only redraws. A build with `RD_BUILD_FONT` compiles one font set and ignores the font setting, and mode 0 ignores avoidance. A build with `RD_BUILD_LOG=1` logs the settings as two `RD settings` lines with their source: d for the defaults, p for the stored blob, and m for a message.

## Scheduling

Interactive Web mode renders up to 30 times per second. It checks elapsed compute time after each complete step and yields after approximately 8 ms. One complete step can exceed the budget. The Speed slider sets the steps attempted per frame within that budget, and the 100-step advance runs up to 8 steps per frame within it.

The Web no longer simulates the watch's startup, minute-work queue, or backlight scheduling. It remains an interactive comparison view. The exported `config.h` retains the watch's scheduling constants, and settings JSON records the minute-step count.

The watch uses SDK BacklightService and AppFocusService. It does not subscribe to accelerometer data. Startup runs in timer slices for `RD_STARTUP_MS` (30 s) after launch or a settings change that restarts the field, or until `RD_STARTUP_STEPS_MAX` (2,500) steps, about 45 s at the measured rate, whichever comes first, which is about 1,650 steps in mode 3 on the physical Pebble Time 2. A minute change during the startup is covered by the startup steps, and only the steps it is still owed at the deadline run after it. The deadline is wall time since launch, so time spent unfocused during the startup counts against it. Minute updates rebuild the digit mask and raise the pending steps to 300 (16 more without avoidance). While work is pending, each callback runs steps until a 30 ms budget is used, checked after every complete step (three steps of about 14 ms in mode 3), then reschedules itself 1 ms later. The layer is marked dirty once another slice would pass 50 ms since the last mark, which gives about 20 frames per second against the OS ceiling of about 27, and when the queue empties. Backlight animation runs the same 30 ms slices and 50 ms redraws for at most five seconds, and draws the last computed steps when the window ends. Focus loss cancels timers and ends a backlight window, and backlight-on is ignored while unfocused. Focus restoration resumes pending work. Backlight-off cancels animation while pending startup or minute work remains eligible for timer execution. A separate five-second timer bounds each backlight animation window. The field is blitted into the framebuffer as ARGB8 rows from `rd_row_rgb2` with `RD_RENDER_FLAGS` (interpolated in mode 3) within the unobstructed bounds, and the clock fonts are loaded at launch and when the font setting changes. A restart resets the startup accounting, so the `RD startup` lines describe the latest startup, while the minimum free heap and the clock fault flag cover the whole session.

Timing uses the public `time_ms` API. The emulator's wall-clock seconds and tick-derived millisecond component can be discontinuous. Negative or unexpectedly large deltas end the current slice and mark timing diagnostics invalid. Such values must not be interpreted as a valid benchmark or used to select a production mode. The watch measured the 30 ms slices and 50 ms frames of this pacing directly ([Validation](validation.md)). Production builds have no logs. A build with `RD_BUILD_LOG=1` (or `RD_BUILD_PROFILE=1`, `RD_BENCH`, or `RD_FRAME_BENCH`) logs `RD init` at launch, four `RD startup` lines when the startup and any refill it still owes have finished (validated wall time, steps per second times 10, the average step, field, and text times, the minimum free heap, and whether a focus loss or a gap of 5 s or more between slices interrupted the run or the clock invalidated it), an `RD mode` progress line every 256 steps (`RD prof` lines with `RD_BUILD_PROFILE=1`, which also runs a clock calibration loop), and `RD light` with the steps and frames of each backlight window.

## Memory reporting

The Web UI shows one memory figure for the selected implementation: the total core allocation reported by the C core for the Wasm modes (fields, scratch rows, control data, the rendering rows and tables, alignment, and the digit mask levels), or the four JavaScript concentration arrays for Float32. The watch's clock mask bitmap is a separate allocation outside the core. Build sizes, compiler stack reports, and the physical measurement of the watch (startup, steps per second, minimum free heap) are in [Validation](validation.md) and `public/reports/comparison.json`. Runtime minimum free heap already includes allocations and must not be added to an estimate of remaining heap.

The acceptance thresholds are a 128 KiB app region and at least 16 KiB minimum free heap during normal operation. Compiler stack reports describe application functions. OS and library stack contributions are additional. Mode 3 is the watch build.
